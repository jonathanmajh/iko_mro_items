# Architecture

This document describes the high-level architecture of the **EAM Spare Parts** application (package name `iko_utility`). It is an [Electron](https://www.electronjs.org/) desktop application that helps Reliability engineers manage, validate, translate, and upload MRO (Maintenance, Repair, and Operations) spare part master data in IBM Maximo.

## Overview

The application is a classic **three-layer Electron architecture**:

```
┌────────────────────────────────────────────────────────────────────┐
│                           Main Process                              │
│                              main.js                                │
│   window lifecycle · IPC handlers · file dialogs · auto-update      │
│           Firestore usage tracking · autoupdater                    │
└───────────────────────────────┬────────────────────────────────────┘
                                │ IPC (ipcRenderer / ipcMain)
┌───────────────────────────────┴────────────────────────────────────┐
│                         Renderer Process                            │
│                   renderer/*.html + renderer/*.js                   │
│   UI (Bootstrap 5) · DOM event wiring · WorkerHandler messaging     │
└───────────────────────────────┬────────────────────────────────────┘
                                │ Web Worker (postMessage)
┌───────────────────────────────┴────────────────────────────────────┐
│                        Worker Thread                                │
│                        renderer/worker.js                           │
│   dispatches every long-running / blocking task (DB, API, Excel)    │
└───────────────────────────────┬────────────────────────────────────┘
                                │
        ┌───────────┬───────────┼───────────────┬─────────────┐
        ▼           ▼           ▼               ▼             ▼
   Maximo API   SQLite DBs  Excel (xlsx)   Firestore      GitHub
   (REST/OSLC) (better-     (exceljs)      (usage logs)   (updates)
                 sqlite3)
```

Key design points:

- **The UI thread never does heavy work.** All database access, network calls to Maximo, and Excel processing happen inside a Web Worker so the renderer stays responsive.
- **Both main and renderer processes** share the same `assets/` modules via `require()`.
- Heavy compute (image processing via `jimp`, batch uploads, data sync) runs off the main thread.
- State is persisted locally in **SQLite databases** and the **browser `localStorage`** (theme, user site, power-user mode).

## Process Architecture

Electron gives the app two runtime processes:

### Main process (`main.js`)

The single entry point. Responsibilities:

- Creating and managing the primary `BrowserWindow` and the modal Settings window
- Wiring `ipcMain` handlers exposed to renderers:
  - `write-file` – writes an email (`.eml`) generated by an item request to disk and opens it
  - `openSettings`, `getVersion`, `getPath`
  - `select-to-be-translated`, `select-excel-file`, `select-translations` – native file-picker dialogs
  - `loading`, `start_item_module`, `start_observation_template`, `start_item_translate`, `start_asset_translate` – in-app navigation by loading the matching renderer HTML
- Instantiating the `Firestore` client and logging the `Start App` usage event
- Starting the auto-updater after the first frame loads

Security notes: `nodeIntegration: true` and `contextIsolation: false` are enabled on both windows. This is intentional here so the renderer can `require()` the `assets/` modules directly, but it is a notable risk and should be revisited (see DEVELOPMENT.md).

### Renderer process (`renderer/*.html` + `renderer/*.js`)

Each HTML page is a distinct "module" (screen) loaded into the main window by the main process IPC navigation handlers:

| HTML | Purpose |
|------|---------|
| `start_page.html` | Launch/login gate. Checks Maximo credentials, then loads the item module |
| `item_main.html` | The primary Item Tool (search, validate, request, upload, batch upload, images) |
| `observation_template.html` | Observation list comparison against Maximo (produces import spreadsheets) |
| `asset_translation.html` | Translates PM / JP / asset descriptions into CSV import files |
| `setting.html` | Settings/modal window (refreshing translation definitions) |

Every page includes `assets/common.js`, which provides shared UI helpers: theme management, `Logging`, `ProgressBar`, `Toast`, the `Item` class, and the `WorkerHandler` used to talk to the worker thread.

### Worker thread (`renderer/worker.js`)

A single Web Worker that is the **orchestrator of all heavy work**. The renderer's `WorkerHandler.work(params, callback)` posts a message whose first element is a command string; `worker.js` switches on that string and instantiates the appropriate service class. See the "Worker command protocol" section below.

## Key Components

### Maximo API client (`assets/maximo.js`)

Thin wrapper over the Maximo OSLC REST API, targeted at the environment URL from `constants.js` (`CONSTANTS.ENV`). Uses `fetch` and authenticates with an `apikey` header set to the user id.

Endpoints used:

- `os/iko_meter` – enumerate condition meters / domain definitions
- `os/iko_alndomain` – enumerate observation domain values
- `os/iko_inventory` – delta fetch of inventory (`fetchmodedelta=1&lastfetchts=...`)
- `os/mxitem` – delta fetch of item master records (9-series), current/latest item number, item existence
- `os/IKO_COMPMASTER` – delta fetch of manufacturers
- `os/IKO_ITEMMASTER` – create/update item master (XML `importfile` action)
- `os/iko_location` – add item to a storeroom (`addAnItemToStoreroom` WS method)
- `api/whoami` – credential / login check
- `script/IKO_PROXY` – arbitrary proxied URL fetch (used by `remotedb.js` and image work)
- item image upload via `mxitem/<id>` `system:addimage`

`getNewItems`, `getNewInventory`, and `getNewManufacturers` all follow a **delta-sync** pattern: they page through results (`pageno`, `oslc.pageSize`) and return the highest timestamp so the caller can store it as the "version" for the next incremental fetch.

Images are padded to a square and downscaled (max 1024px) with `jimp` before upload (`padImage`).

### Local data layer (SQLite via `better-sqlite3`)

Multiple SQLite files live in the OS user-data directory (`%APPDATA%\EAM Spare Parts` on Windows, `~/Library/Preferences/EAM Spare Parts` on macOS, `~/.local/share/EAM Spare Parts` on Linux):

| File | Class | Contents |
|------|-------|----------|
| `program.db` | `Database` (`indexDB.js`) | `itemCache`, `inventoryCache`, `manufacturers`, `abbreviations`, `workingDescription`, `itemDescAnalysis`, `settings` |
| `obserlist.db` | `ObservationDatabase` (`better-sqlite.js`) | `meters`, `observations`, `jobtasks` |
| `translist.db` | `TranslationDatabase` (`item-translation-sqlite.js`) | `translations` (english -> lang_code dictionary) |

Tables are created (with the schema defined in `indexDB.js#createTables`) on first run and refreshed when a newer remote database is detected.

**Why SQLite**: Maximo holds 100k+ item records; fetching them live is too slow. The app keeps a locally cached, searchable copy built via delta sync and through an initial bundled Excel spreadsheet (`excel.js#getItemCache`).

### Remote database distribution (`assets/remotedb.js`)

To keep the cache fresh without loading all of it from Maximo, a pre-built `program.db` is packaged into a `program.zip` hosted at a Cloudflare Worker URL (`https://iko-proxy.jonathanmajh.workers.dev/program.zip`). On startup, `checkItemCache` compares a `.version` file against the stored version; if newer, it downloads the zip (through the Maximo proxy) and unzips the `.db` via `@zip.js/zip.js`, then merges its tables into the local DB via SQL `ATTACH DATABASE` in `indexDB.js#loadRemote`.

### Validation (`assets/validators.js`)

`Validate.validateSingle(desc)` parses a comma-separated description and:

1. Splits into phrases, finds a known manufacturer (looked up from the end of the string), normalizes it to its short name.
2. Replaces abbreviated phrases / words with their expanded forms using the `abbreviations` table.
3. Assembles the result into up to three JDE/description segments (`main`, `ext1`, `ext2`) with a 30-character-per-segment limit, plus a combined Maximo description.

`itemOccurrence` and `matchAndScore` (in `indexDB.js`) power the related-item search and item-type confidence analysis.

### Translation (`item_translation/*` and `asset_translation/*`)

Two independent translation features:

- **Item description translation** (`item-translation.js`): context-aware. It tries to translate the longest matching phrase in the dictionary first, then falls back word-by-word; anything unmatched is reported into a `missing` list. Works for a selected target language (`selected-language`).
- **Asset / PM / JP translation** (`asset_translation_main.js`): parses PM/JP numbers (`NumParser`) into components (site, route, frequency, work type, labor, lifecycle) and rebuilds a translated description from lookup tables in the workbook, then emits four CSVs (`location.csv`, `asset.csv`, `jobplans.csv`, `pms.csv`) formatted as Maximo `IKO_Import` files, plus a translation `log`.

### Usage tracking (`assets/firestore.js`)

Anonymous-ish usage events (`Start App`, `Search Item`, `Add to Inventory`, `Request Item`) are written to a Firebase Cloud Firestore `events` collection. The renderer sends these via IPC (`firestore-log`); the main process forwards them to `Firestore.log()`.

## The Web Worker Command Protocol

`renderer/worker.js` is a command dispatcher. The renderer builds a `[command, ...args]` array, posts it to the worker, and the worker replies with `[status, ...payload]` messages. `WorkerHandler.work` interprets these replies and updates the UI (toasts, progress bar, log table, table cell statuses).

Commands handled:

| Command | Purpose |
|---------|---------|
| `validSingle`, `validBatch` | Validate one / a batch of descriptions |
| `update` | Rebuild `manufacturers` / `abbreviations` tables from an Excel file |
| `createDatabase` | Create the abbreviation + manufacturer tables |
| `findRelated` | Find related items in the cache by description |
| `interactive`, `writeDesc`, `writeNum` | Read / write descriptions or item numbers in an Excel workbook |
| `checkItemCache` | Delta-sync cache + inventory/item/manufacturer data from Maximo (startup) |
| `processObservationList`, `getMaximoObservation`, `compareObservLists` | Observation template workflow |
| `refreshTranslations`, `batchTranslate`, `translateItem` | Translation features |
| `nonInteractive`, `saveProcessed` | Non-interactive batch description processing |
| `loadItem` | Load an item from the cache |
| `translatepms` | Asset/PM/JP translation |
| `getCurItemNumber` | Get the latest item number for a series |
| `uploadItems`, `uploadInventory`, `uploadImages`, `checkUser` | Maximo writes and auth |

Worker messages back to the renderer:

| Status | Meaning |
|--------|---------|
| `result` | Success, with a data payload; callback invoked |
| `error` | Fatal failure; red toast + progress bar set to 100 |
| `fail` | A non-fatal failure; logged |
| `progress` | Update the progress bar + log info |
| `warning` / `info` / `debug` | Toast / log entries |
| `update` / `updateColors` | Mutate specific table cells (status icons, red-highlight invalid cells) |
| `runCallback` | Invoke the renderer callback directly with a payload |
| `upload-error` | Upload failure typed by HTTP status code |

## Data Flows

### Startup / login (`start_page.js`)

1. `window.onload` → `tryLoginItem` runs `checkUser` in the worker.
2. `checkLogin` inspects the result: success (`status[0] === 0`) stores `userSite` in `localStorage` and calls `openItem(true)`; failure shows the login modal.
3. `openItem` runs `checkItemCache` (delta sync + remote DB refresh) then sends `loading` to switch to `item_main.html`.
4. "Continue" skips login and loads the item module with the existing cache (`noMaximo`).

### Item workflow (`item_main.html`)

The Item Tool supports two roles:

- **Normal user**: requests items (auto-generates an email opened via the OS mail client), searches, validates, and view; upload buttons are hidden.
- **Power user**: toggled by clicking the "secret button" 5 times; additionally gets single upload, batch upload, image upload, and commodity/GL fields.

Core operations:

- **Search** → `findRelated` → scored related-item table with infinite scroll (`loadRelated`).
- **Validate** → `validSingle` → triple description + confidence analysis (`calcConfidence`, based on `itemDescAnalysis` occurrence counts).
- **Request** → builds an email, `ipcRenderer.send('write-file')` opens the `.eml`.
- **Single upload** → `uploadItems` with a new 7-digit 9-series item number; links back into Maximo.
- **Batch upload** → paste tab-separated rows into `batch-items-table`, validate columns (`updateTableColors`), `uploadItems` with per-item status icons; new item numbers written back to the table.
- **Image upload** → `uploadImages` → pads/validates and uploads via `system:addimage`; skips if an image already exists.

### Observation template (`observation_template.html`)

1. Read an observation list Excel file (`processObservationList`), storing meters/observations into `obserlist.db`.
2. Fetch meters/observations from Maximo (`getMaximoObservation`).
3. `compareObservLists` diffs local vs Maximo and writes a set of Maximo `IKO_Import` worksheets (`ChangeCondDomDef`, `RemoveCondDomDef`, `ChangeCondDomVal`, `RemoveCondDomVal`, `ChangeCondMeter`, `RemoveCondMeter`, `ChangeJobTask`, `RemoveJobTask`) to a chosen output file.

## Deployment / Update Channel

- **Packaging**: Electron Forge (Squirrel for Windows, zip for macOS). Icon: `AppIcon.ico` / `AppIcon.png`.
- **Publishing**: `package.json` config points at the GitHub repo; GitHub Actions (`release.yml`) runs `npm run publish` on tags / releases.
- **Updates**: Squirrel-based `autoUpdater` feed is `https://mro-update.vercel.app/update/<platform>/<version>`. On Windows it checks for updates; if the `autoUpdater` errors, it falls back to querying the GitHub latest release and prompting the user (see `autoupdater.js`).

## Configuration

All runtime configuration is centralized in `assets/constants.js`. Environment-sensitive values are sourced from environment variables with **production-safe defaults**:

- `ENV` – the Maximo environment hostname (UAT vs production), from `MAXIMO_ENV`, defaulting to production
- `OPEN_DEV_TOOLS` – opens DevTools at launch when `OPEN_DEV_TOOLS=true` (default off)
- `REPLACEMENTS` – smart-quote / hyphen normalization mapping used when sanitizing descriptions
- `FIREBASECONFIG` – Firebase project settings for usage tracking; the API key is supplied via `FIREBASE_API_KEY`
- Local user-data paths are resolved centrally via `assets/paths.js` rather than being hard-coded per module

## Known Architectural Traits / Notes

- `contextIsolation: false` + `nodeIntegration: true` is a security trade-off that keeps the architecture simple but is not recommended for production-facing Electron apps.
- `assets/excel.js` exports a single `Spreadsheet` class consolidating the former `ExcelReader` (item cache/batches) and the old `Spreadsheet` (observation/jobtask/translation import-export). `better-sqlite.js` exports `ObservationDatabase`.
- `gitignore` excludes `program.db`, `obserlist.db`, and the `out/` build directory.
- Some modules are marked legacy/deprecated in comments (e.g. `Spreadsheet.getDescriptions`, `item-translation.translate`) — these are work-in-progress.
